# Финансовый дашборд по маркетплейсам (ВБ + Ozon)

Мультиклиентский пайплайн: тянет данные напрямую из API Wildberries и Ozon,
приводит к единой схеме, считает финансовые метрики (воронка, удержания,
товары с красными зонами, план-факт) и отдаёт их в веб-дашборд.

> **✅ 2026-07-15: миграция на новый WB Finance API выполнена.** Старый
> `GET /api/v5/supplier/reportDetailByPeriod` в этот день отключается. Пайплайн
> по умолчанию использует новый метод
> `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`
> (`WildberriesFinanceClient` + `normalize_wb_finance_row`). Схема ответа —
> camelCase (`rrdId`, `vendorCode`, `forPay`, …), взята из опубликованной
> OpenAPI-спецификации WB. Старый эндпойнт остаётся доступен как запасной:
> `python -m etl.pipeline ... --wb-api statistics`. На первом реальном синке
> всё же сверьте сырой ответ с маппингом. Одно отличие нового отчёта:
> «продвижение в рублях» (`supplier_promo`) в нём отсутствует — ДРР берите из
> рекламного API или из CSV-загрузки.

## Архитектура

```
connectors/   HTTP-клиенты WB Finance API (+ legacy Statistics) и Ozon Seller API
etl/          нормализация сырых отчётов в единую схему + оркестратор пайплайна
storage/      SQLite-схема (multi-tenant: каждая строка помечена client_id)
analytics/    агрегация метрик (воронка, удержания, товары, динамика, план-факт)
dashboard/    FastAPI backend + статический фронтенд
tests/        нормализация, метрики, HTTP-логика коннекторов (мок-транспорт),
              storage/pipeline (идемпотентность, изоляция клиентов), HTTP API
```

## Установка

Требуется Python 3.10+ (код использует синтаксис `str | None` в аннотациях
типов, который на более старых версиях падает с `TypeError` при импорте).

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Онбординг клиента

1. Клиент выдаёт вам API-ключ Wildberries (личный кабинет → API) и
   `Client-Id`/`Api-Key` Ozon (личный кабинет → Настройки → API-ключи).
2. Скопируйте `clients.example.json` в `clients.json` (файл в `.gitignore`,
   не коммитится) и впишите ключи клиента:

```bash
cp clients.example.json clients.json
```

## Загрузка данных

Два способа, работают вместе.

**Через API маркетплейсов** (нужны API-ключи в `clients.json`):

```bash
.venv/bin/python3 -m etl.pipeline --client demo --date-from 2023-10-01 --date-to 2023-12-31
```

**Из CSV-файлов** — вкладка «Загрузка» в дашборде: выберите маркетплейс,
загрузите CSV-выгрузку из кабинета. Кодировка (cp1251/UTF-8), разделители
(`;`/`,`), русские форматы чисел («1 234,56») и дат (дд.мм.гггг) исправляются
автоматически; каждое исправление показывается рядом со строкой. Строки,
которые исправить не удалось, помечаются ошибкой — их можно поправить прямо
в таблице и импортировать повторно. Файл можно удалить — его данные уйдут из
дашборда (откат). Строки с ошибками выгружаются отдельным CSV.

Если в выгрузке есть колонки «Категория» (формат `Раздел/Подкатегория`) и
«Бренд», они подхватываются и включают сквозную группировку и разбивку по
разделам на вкладках «Товары» и «Возвраты».

**Себестоимость** — отдельная плашка на вкладке «Загрузка»: CSV со столбцами
`SKU` и себестоимостью за штуку («Полная себестоимость за шт»,
«Себестоимость закупки за шт» или просто «Себестоимость»). После загрузки
весь анализ (KPI, ABC, карточки товаров, «где теряются деньги») пересчитывается
по **чистой прибыли** (`к выплате − себестоимость проданного`), а не по обороту.
Файл можно убрать — метрика вернётся к «к выплате».

Оба пути идемпотентны — повторный запуск/импорт не задваивает строки
(апсерт по `client_id + marketplace + raw_ref`).

## Запуск дашборда

```bash
.venv/bin/uvicorn dashboard.server:app --port 8765
```

Откройте `http://127.0.0.1:8765`, укажите `client_id` в фильтре слева.

## Известные ограничения

- **Дашборд без авторизации.** `client_id` — открытый query-параметр:
  любой, кто достучится до сервера, может подставить чужой `client_id` и
  увидеть данные другого клиента. Осознанно не исправлено, пока дашборд
  разворачивается как отдельный экземпляр на одного клиента. **Если/когда
  на одном инстансе появится больше одного клиента — до этого момента
  нужно добавить авторизацию** (проще всего — токен на клиента вместо
  открытого `client_id` в фильтре).
- Названия полей в отчётах WB и Ozon указаны по документации на момент
  написания — оба API меняли схему полей и раньше. Перед первым реальным
  запуском на новом клиенте сверьте сырой ответ API с маппингом в
  `etl/normalize_wb.py` / `etl/normalize_ozon.py`.
- Классификация статей Ozon (`logistics`/`storage`/`promotion`) идёт по
  ключевым словам в названии сервиса — при появлении новых кодов услуг
  проверьте, что они попадают в нужную корзину.
- SQLite подходит для одного продавца/небольшого числа клиентов на
  инстанс; для продакшен-мультитенантности на многих клиентов стоит
  перейти на Postgres — большая часть схемы переносится как есть, кроме
  `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite-специфичный синтаксис,
  в Postgres — `GENERATED ALWAYS AS IDENTITY`).
- Идемпотентность upsert'а держится на уникальности `raw_ref` (WB `rrd_id`
  / Ozon `operation_id`) в пределах клиента и маркетплейса. Это значения,
  которые генерирует сама площадка — если ВБ или Ozon когда-либо переиспользуют
  `rrd_id`/`operation_id` для другой операции (не подтверждено, но и не
  исключено документацией), повторный upsert тихо перезапишет более раннюю
  операцию. Если после синка появятся расхождения в суммах — это первое,
  что стоит проверить.
