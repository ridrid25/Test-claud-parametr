# Отчёт: anthropics/commerce-agents (merchant-agent) применительно к «Финансовому срезу — Маркетплейсы»

Дата: 05.09.2026. Исследован репозиторий `github.com/anthropics/commerce-agents`,
коммит `fd4d592` («building commerce agents using claude», 31.08.2026), лицензия
Apache 2.0 (файл `LICENSE` — стандартный текст Apache License 2.0; в каждом
исходнике `SPDX-License-Identifier: Apache-2.0`). README прямо говорит: это
эталонная реализация, «не сопровождается и не принимает вклады».

Всё ниже — по коду репозитория. Где утверждение — моя оценка, а не факт из
кода, это помечено словом «оценка». Пути даны относительно корня репозитория.

---

## Коротко

- **Скиллы** — пять текстовых файлов `SKILL.md`, без исполняемого кода.
  Маркетинговый скилл пишет черновики кампаний и распределяет бюджет, но
  **ничего не отправляет и не запускает**: «Scheduling, sending, and spending
  happen in the host's campaign system after approval».
- **MerchantBackend** — абстрактный Python-класс: 8 методов чтения, 5 методов
  «stage_*» (подготовить изменение), 3 метода очереди изменений и 3
  необязательных. Из выгрузок WB/Ozon полностью закрываются 2 чтения,
  частично — 5, одно (кампании) — нет.
- **Режима «только чтение» как настройки в коде нет.** Фраза README про «восемь
  методов чтения, а записи отказывают» реализуется руками: методы записи в
  своём бэкенде бросают исключение `ChangeNotApplicable`. Вторая линия защиты —
  включённое по умолчанию `require_host_approval`: применить изменение без
  отметки человека агент не может ни на одном пути запуска.
- **Модель данных — под собственный интернет-магазин** (трафик, конверсия,
  кампании с бюджетом, карточки товара). Комиссии, логистики, хранения,
  штрафов, удержаний и «к выплате» в типах **нет вообще**. Себестоимость и
  остатки — есть.
- **Хранилища и планировщика нет**: сессии и подготовленные изменения живут в
  памяти процесса, память агента — один JSON-файл, дайджест запускается внешним
  cron. Ключ Anthropic — переменная окружения на сервере.
- **Принцип «файлы не уходят из браузера» с этим агентом соблюсти буквально
  нельзя**: модель должна увидеть цифры. Можно соблюсти ослабленную версию —
  «сырые файлы не уходят, уходят только агрегаты, сервер ничего не хранит».
  Подробно — раздел 4.

## 1. Что умеют скиллы `merchant-agent/skills` — по файлам

Проверено `find merchant-agent/skills -type f`: ровно пять файлов, все —
`SKILL.md`. Вспомогательных скриптов, Python или TypeScript в скиллах нет.

### Как скиллы устроены технически

Загрузчик — `commerce-common/commerce_common/skills.py`: скилл это каталог с
`SKILL.md` (YAML-шапка `name` + `description`, дальше текст). Ничего, кроме
`SKILL.md`, из каталога не читается — поэтому исполняемого кода в скиллах
быть не может по конструкции. В системный промпт попадает только индекс
(имя + описание); полный текст модель получает вызовом инструмента
`load_skill`. Скиллы не имеют собственных инструментов — они лишь объясняют
модели, какие общие инструменты из `merchant-agent/core/merchant_agent/tools/registry.py`
вызывать и как оформлять ответ. Все проверки (гейты, лимиты) — в Python, не
в скиллах.

### 1.1. `marketing-campaigns/SKILL.md` — маркетинг и кампании (43 строки)

Описание: черновики кампаний и объявлений «как подготовленные изменения» — от
сезонных акций до lifecycle-рассылок (win-back, «до прибытия», «последний
шанс»), выбор аудитории и площадки по намерению, распределение бюджета между
кампаниями, разбор результатов «с оговорками об атрибуции».

Что делает по тексту:

- Читает `get_campaign_performance` (spend, revenue, статус), `get_listing`
  (факты о товаре для текста), память (`recall_memories` — «голос бренда»).
- Пишет черновик через `stage_campaign`: название, цель, аудитория, бюджет,
  текст до 600 символов, даты. Это **запись в очередь изменений, не запуск**.
- Ключевые правила (цитаты из файла):
  - строка 10: «A review reads the campaign figures; a draft, a copy change, or
    a budget move is staged. Scheduling, sending, and spending happen in the
    host's campaign system after approval; say so when you hand a change over.»
  - строка 15: атрибутированную выручку называть «заявлением канала», а не
    фактом, и оговаривать это, где оно меняет вывод;
  - строка 17: писать в голосе бренда из памяти; если не сохранён — спросить
    один раз;
  - строка 18: факт о товаре берётся только из карточки или от оператора;
    характеристика или превосходная степень без источника — в текст не попадает;
  - строка 22: у каждого черновика одна аудитория и одна измеримая цель;
  - строка 34: общий бюджет фиксирован — предложение «добавить одной кампании»
    обязано назвать, у какой отнять;
  - строка 40: единственный guardrail здесь — лимит бюджета кампании
    (по умолчанию 10 000 в `config.py`).
- Про email: слова «email» в файле нет. Канал — свободная строка `channel` в
  типе `Campaign`. Интеграций с почтовыми сервисами или рекламными кабинетами
  в репозитории нет — это факт, а не оговорка.

**Вывод для нас:** маркетинговый скилл ждёт данных о кампаниях (бюджет,
расход, выручка по кампании). В отчёте о реализации WB/Ozon есть только
общая сумма «продвижение» без разбивки — скиллу не с чем работать.

### 1.2. `pricing-promotions/SKILL.md` — цены и промо (43 строки)

Описание: изменения цены внутри guardrail'ов магазина, рекомендации от
спроса/темпа продаж, промо с охватом, глубиной и датами, уценка неликвида,
предпросмотр маржи до подготовки изменения.

- Обязательно читает `get_pricing_context` по каждой карточке: текущая цена,
  себестоимость, `margin_pct`, допустимый диапазон, два лимита
  (`max_price_delta_pct` — по умолчанию 20 %, `max_promotion_discount_pct` —
  по умолчанию 50 %), сигнал спроса.
- Строка 16: **«Quote margins; do not compute them»** — маржу модель не
  считает сама, а берёт из бэкенда. Это удобно: формулу маржи задаём мы.
- Строка 15: при просьбе выйти за лимит — назвать лимит и предложить цифру
  внутри него; не подставлять «урезанный» вариант молча.
- Строка 30: промо ставится в очередь только с охватом, глубиной и датой
  окончания; бессрочная или общая скидка — вопрос оператору.
- Пишет через `stage_price_update` / `stage_promotion`.

### 1.3. `catalog-listings/SKILL.md` — контент карточек (42 строки)

Описание: заголовки, описания, полнота атрибутов, категория, аудит качества
контента и массовые правки.

- Перед правкой обязателен `get_listing`. Аудит — через `search_listings` с
  фильтром `content_quality`.
- Строка 16: значение атрибута берётся только из карточки или от оператора;
  «правдоподобное» значение — фабрикация, поле оставить пустым.
- Строка 36: цена и остаток в этом потоке не редактируются — это зашито в код
  (`listing_update_blocked_fields=("price","stock")` в `config.py`).
- Пишет через `stage_listing_update`; лимит поля 2000 символов.

### 1.4. `inventory-operations/SKILL.md` — остатки, алерты, утренний дайджест (48 строк)

Описание: контроль остатков и доступности, реакция на алерты «мало» и
«не продаётся», разбор проблемных заказов (задержки, всплеск возвратов,
жалобы), ежедневный брифинг оператора.

- Строка 14: брифинг строится **только** из `get_inventory_alerts`,
  `get_order_issues`, `get_business_snapshot` и `get_pending_changes`,
  вызванных в этом же разговоре; вчерашний брифинг и память — не источники.
- Строка 23: точки перезаказа и страховые запасы — настройка хост-системы,
  агент их не задаёт.
- Строка 27: пополнение/пауза/активация — через `stage_inventory_action` с
  явным количеством и обоснованием («60 единиц — примерно три недели при 3 в
  день»). Лимит `max_restock_quantity` = 500.
- Строка 33: по неликвиду предлагать три варианта по имени: оставить, уценить,
  снять; уценка передаётся скиллу цен.
- Выход — компонент `present_digest` (3–6 записей, ранжированных «по деньгам
  под риском, затем по срочности»).

### 1.5. `performance-insights/SKILL.md` — «почему метрика двинулась» (48 строк)

Описание: объяснение состояния бизнеса — почему изменилась метрика, какой
сегмент это дал, темп против сопоставимого периода, прогресс к целям
оператора; вопросы по продажам, трафику, конверсии, покупателям.

- Первым — `get_business_snapshot`, затем `query_metrics` по сегментам.
- Строка 16: серию, которой у бэкенда нет, называть недоступной и говорить,
  какой вопрос остался открытым.
- Строка 19: последняя дата серии — граница данных; период за ней —
  неполный, сравнивать с полным нельзя без оговорки.
- Строка 31: сначала подтвердить движение, потом объяснять (неполный период,
  дыра в серии, необычная база объясняют многие «падения»).
- Строка 35–36: причиной называть только то, что совпадает по времени и
  сегменту; иначе — корреляция. Уверенность — словами: «finding», «lead»,
  «not visible in the data».
- Строка 40: не выдумывать цель, которую оператор не называл.
- Отдельно (вне скилла) при `enable_analysis=True` есть инструмент
  `run_analysis` — делегат с собственным циклом, который умеет выполнять
  только `SELECT` через `MerchantBackend.execute_analysis_query`.

## 2. Интерфейс MerchantBackend: что требует и что закрывается выгрузками

Файл `merchant-agent/core/merchant_agent/backend.py`, класс
`MerchantBackend(ABC)`. Все методы `async`, первый параметр — контекст
сессии (`session_id`, `merchant_id`, `operator`, время). Докстринг класса:
чтения свободны, `stage_*` записывают предложение, не трогая живое
состояние, **только `apply_change` меняет что-то**; методы вызывают системы
продавца на сервере с учётными данными хоста — модель токен не видит.

### 2.1. Восемь методов чтения (все обязательные)

| Метод | Возвращает | Из WB/Ozon + себестоимость + остатки | Статус (оценка) |
|---|---|---|---|
| `get_business_snapshot(period)` | `BusinessSnapshot`: `sales`, `orders`, `traffic`, `conversion_rate`, `average_order_value`, `*_change_pct`, `alerts`, `note` | продажи — да (реализация − возвраты); заказов нет, есть штуки; трафика и конверсии нет → `None` + `note` (так и задумано: «a figure the store's systems cannot supply is None, never a stand-in zero») | **частично** |
| `query_metrics(metric, period, granularity, segment)` | `MetricSeries`: точки `date`/`value`, `unit`, `segment`, `note` | серии по дате есть: продажи, штуки, возвраты; сегменты — категория, бренд, SKU, маркетплейс. Имя метрики — свободная строка, можно вернуть `commission`, `logistics`, `payout`, но промпт и скиллы таких метрик не знают | **закрывается** для продаж/штук/возвратов |
| `get_campaign_performance(campaign_id)` | `list[Campaign]`: `budget` (обязателен), `spend`, `revenue`, `status`, даты | в отчёте только общая сумма «продвижение» без кампаний | **нет** (можно одну синтетическую «кампанию» с `revenue=None` и оговоркой) |
| `search_listings(query, filters, limit)` | `list[Listing]`: `listing_id`, `title`, `status`, `price` (обязателен), `stock`, `category`, `attributes`, `content_quality` | SKU, название, категория, бренд, остаток — да; текущей цены карточки нет (только фактическая цена продажи); качества контента нет | **частично** |
| `get_listing(listing_id)` | `ListingDetails`: + описание, отзывы, `sales_last_30d`, `return_rate_pct`, `missing_attributes`, варианты | продано за 30 дней и % возвратов — да; описаний и отзывов нет | **частично** |
| `get_inventory_alerts()` | `list[InventoryAlert]`: `stock`, `threshold`, `days_of_cover`, `sales_last_30d`, вид `low_stock`/`slow_mover` | остатки + продажи — вычисляется (дни покрытия = остаток / продажи в день) | **закрывается** |
| `get_order_issues()` | `list[OrderIssue]`: `delayed` / `return_spike` / `buyer_message` / `damaged`, `order_id`, текст | всплеск возвратов по SKU — можно; номеров заказов и текстов нет | **частично** |
| `get_pricing_context(listing_id)` | `PricingContext`: `current_price`, `unit_cost`, `margin_pct`, `min/max_price`, лимиты, `demand_signal` | себестоимость — да; маржу считаем мы (тип позволяет задать маржу после удержаний, а не «цена − себестоимость», как в примере); текущей цены нет | **частично** |

Итого: полностью — 2 (`query_metrics` по продажам/штукам/возвратам,
`get_inventory_alerts`), частично — 5, не закрывается — 1
(`get_campaign_performance`).

### 2.2. Методы записи (обязательные, но для нас — отказ)

`stage_listing_update`, `stage_price_update`, `stage_inventory_action`,
`stage_promotion`, `stage_campaign`, а также `get_pending_changes`,
`apply_change`, `discard_change`. Все помечены `@abstractmethod`, то есть
**не реализовать их нельзя** — Python не создаст объект. Для пилота на
файлах они пишутся заглушками, которые отказывают (см. раздел 3).

### 2.3. Необязательные

`execute_analysis_query(sql)` и `get_analysis_schema()` — по умолчанию
`None`; в примере реализованы на SQLite в памяти с разрешением только на
чтение. `get_merchant_context()` — контекст магазина в промпт, включая список
ограничений данных (`DataLimitation`: «нет трафика», «история 8 недель»).
Для нашего случая это самый полезный необязательный метод.

### 2.4. Чего в модели данных нет, а в отчёте маркетплейса есть

| Поле отчёта | В MerchantBackend | Как выкрутиться (оценка) |
|---|---|---|
| Комиссия, логистика, хранение, штрафы, прочие удержания | нет | своя метрика в `query_metrics` + свой скилл; `BusinessSnapshot` не расширяется без правки ядра (pydantic без `extra`) |
| К выплате | нет | то же; семантика `sales` другая |
| Возвраты в деньгах | только `return_rate_pct` в процентах | метрика `returns` в `query_metrics` |
| Бренд | отдельного поля нет | `Listing.attributes["brand"]` |
| Себестоимость по SKU | `PricingContext.unit_cost` | закрывается |
| Остатки по SKU | `Listing.stock`, `InventoryAlert.stock` | закрывается (по складам — только суммой) |

Готовых реализаций бэкенда поверх чего-то реального нет: четыре mock'а
(`examples/{retail,travel,telecom,entertainment}/api/mock_merchant.py`) на
JSON-фикстурах в памяти. Ни Shopify, ни CSV, ни БД. Полезный артефакт —
контрактный тест бэкенда `examples/demo_common/tests/contract.py` (677
строк): им можно проверить свою реализацию.

Важно: в этом же репозитории (Test-claud-parametr) уже есть серверный
Python-пайплайн (`connectors/`, `etl/`, `storage/` на SQLite, `analytics/`,
`dashboard/`). Реализация `MerchantBackend` естественно ложится поверх него,
а не поверх браузерного `index.html`.

## 3. Режим «только чтение»: как включается на самом деле

README (строки 177–180): «A merchant pilot implements the eight read methods
and has the writes refuse; digests and metrics then run with no write path.»

**Проверка по коду.** Флага `read_only`, класса `ReadOnlyBackend` или
аналога нет. Поиск по `read_only|readonly|ReadOnly` находит только SQLite
authorizer для аналитики и два названия тестов. Конфиг
`MerchantAgentConfig` объявлен с `extra="forbid"` — неизвестное поле
`read_only=True` упадёт при запуске.

Что есть вместо этого — три механизма, которые надо сложить руками:

**3.1. Исключение `ChangeNotApplicable` в методах записи** — это и есть
«writes refuse». Докстринг `backend.py`: метод для системы, которой у
деплоя нет, бросает `ChangeNotApplicable` с названием того, что не
управляется; исполнитель передаёт это модели. Код обработки
(`executor.py`, строки 137–143):

```python
def domain_error(self, error: Exception) -> ToolOutcome | None:
    if isinstance(error, GuardrailViolation):
        return ToolOutcome.held(GUARDRAIL_GATE, guardrail_block_message(error.violations))
    if isinstance(error, ChangeNotApplicable):
        # Backend text arriving outside the fence: sanitized and capped.
        return ToolOutcome.error(self._sanitize(str(error), 300))
    return None
```

Любое другое исключение (например `NotImplementedError`) даёт модели
сообщение «temporarily unavailable» — она будет предлагать «попробовать
позже». Поэтому заглушки должны бросать именно `ChangeNotApplicable`
с понятным текстом: «этот пилот не меняет цены в кабинете».

**3.2. Переключатели `enable_*`** (`config.py`, строки 37–46):
`enable_listing_edits`, `enable_inventory`, `enable_pricing`,
`enable_campaigns`. Выключенный переключатель убирает инструменты
системы **и чтения, и записи** (комментарий в коде: «removes that system's
read and stage tools on every path»). Выключить все четыре — исчезает вся
очередь изменений, но остаются лишь 4 чтения из 8 (`get_business_snapshot`,
`query_metrics`, `search_listings`, `get_listing`; подтверждено тестом
`tests/test_system_switches.py`). Алерты по остаткам при этом пропадают —
для нас это неприемлемо, значит переключатели не заменяют 3.1.

**3.3. `require_host_approval: bool = True`** (`config.py`, строка 75).
`apply_change` проходит только для изменения, которое хост пометил
одобренным (`gates.py`, `check_apply_change`): отметку ставит кнопка Approve в
демо-портале или `host_approve` в консоли SDK — модель поставить её не
может. На пути Managed Agents вместо этого `permission_policy: always_ask`
на `apply_change` в манифесте `agent.yaml`. Следствие: с настройками по
умолчанию агент может **подготовить** изменение (запись в свой журнал), но
**применить** без человека — нет, на всех трёх путях запуска.

**Итог.** Режим «только чтение» собирается так: восемь чтений реализованы,
восемь методов записи бросают `ChangeNotApplicable`, `require_host_approval`
оставлен включённым. Это ручная сборка по рецепту, а не настройка. Рецепт
описан только в тексте команды плагина Claude Code
(`plugins/commerce-builder/commands/scaffold-commerce-agent.md`, строки
212–215: «live (reads only) → reads call the system; merchant `stage_*`
methods raise `ChangeNotApplicable`»). Права в кабинете площадки агенту при
этом не нужны вообще: бэкенд читает наши файлы или нашу SQLite, а не API WB/Ozon.

## 4. Что ломается из-за «только браузер» и какая минимальная серверная часть возможна

### 4.1. Что именно ломается

1. **Ключ Anthropic.** Все три пути запуска — серверные Python-процессы:
   `AsyncAnthropic` читает `ANTHROPIC_API_KEY` из окружения
   (`orchestrator.py`), Claude Agent SDK — свой CLI, Managed Agents — хостинг
   Anthropic. Ключ в браузере — это ключ, который увидит любой посетитель.
2. **MerchantBackend — это Python.** Ядро `merchant_agent` (гейты, лимиты,
   журнал изменений, сборка промпта — около 3 000 строк с тестами) на JS не
   переносится «бесплатно». Браузерная реализация означала бы переписать ядро.
3. **Состояние между ходами.** Сессии и подготовленные изменения — в
   памяти процесса (`examples/demo_common/sessions.py`, `ChangeLedger`);
   память агента — JSON-файл (`JsonFileMemoryStore`). Всё это — на сервере.
4. **Утренний дайджест** — headless-скрипт `run_morning_digest.py` под
   внешним cron. В браузере, который закрыт, ничего не запустится.
5. **Сам принцип.** Модель не может объяснить падение выплаты, не увидев
   цифры выплаты. Данные уйдут в API Anthropic в любой архитектуре, где
   участвует Claude. Это не техническая, а принципиальная граница.

### 4.2. Можно ли не нарушить принцип «данные не уходят»

Буквально — **нет**. Честная формулировка, которую можно предложить
заказчику: «сырые файлы из кабинета не покидают браузер; агенту уходит
только агрегированная таблица, которую пользователь видит и подтверждает;
сервер ничего не хранит». Это ослабление принципа, и его надо проговорить
с заказчиком отдельно, а не сделать молча.

Минимальная серверная часть под такую формулировку (оценка):

1. **Агрегация остаётся в браузере.** `index.html` уже считает всё сам. Он
   формирует компактный пакет: серия «дата → реализация, возвраты,
   удержания по статьям, выплата», таблица по SKU (без названий, если
   заказчик захочет — только артикулы), остатки, себестоимость. Никаких
   исходных строк отчёта.
2. **Пользователь видит пакет и нажимает «Отправить агенту».** Без явного
   действия ничего не уходит — как сейчас с загрузкой файла.
3. **Тонкий сервер без состояния**: один процесс FastAPI (уже есть в
   `dashboard/`), который принимает пакет, строит `MerchantBackend` **в
   памяти только на время запроса** поверх этого пакета, прогоняет ход
   агента через `MerchantAgent` (Messages API) и возвращает ответ. Ключ
   Anthropic — только на этом сервере. На диск не пишется ничего; логи — без
   тел запросов.
4. **Память агента и «одобрения» — в браузере.** Протокол `MemoryStore`
   (6 методов) и `SessionStore` (6 методов) специально сделаны подменяемыми;
   их можно реализовать так, что состояние ездит в запросе туда-обратно и
   хранится в `localStorage`/IndexedDB пользователя. Сервер остаётся без
   хранилища.
5. **Дайджест по расписанию** при такой схеме невозможен: пока браузер
   закрыт, данных на сервере нет. Либо от него отказаться, либо разрешить
   хранить агрегаты на сервере — это уже другой уровень доверия.

Что **не** решается никакой серверной частью:

- Anthropic API получает агрегаты. Точка. Можно опираться на политику
  Anthropic о неиспользовании данных API для обучения, но это договорная,
  а не техническая гарантия.
- Псевдонимизация (заменять артикулы на коды в браузере и раскодировать
  ответ обратно) снижает чувствительность, но суммы всё равно уходят.
- Вариант «пользователь вводит свой ключ Anthropic, браузер зовёт API
  напрямую» убирает сервер, но требует переписать ядро агента на JS и не
  меняет факта отправки данных. Не рекомендую.

### 4.3. Альтернатива для тех, кому принцип важнее агента

Оставить `index.html` как есть, а агента запускать **на стороне
заказчика**: `docker compose` с FastAPI + тонкий бэкенд поверх его же SQLite
из `storage/`, ключ Anthropic его. Тогда «данные не уходят к нам» — правда, а
«уходят в Anthropic» — осознанный выбор заказчика. Для финансиста-заказчика
это, вероятно, самый честный вариант.

## 5. Трудозатраты и что даёт эффект первым

Оценки в рабочих днях одного разработчика, знакомого с проектом. Тестовый
контур репозитория (`FakeClient`, контрактный тест бэкенда) позволяет
делать всё без расхода токенов до самого конца.

| # | Работа | Дней | Комментарий |
|---|---|---|---|
| 1 | Read-only `MerchantBackend` поверх нашей SQLite (`storage/`) и/или агрегатов из браузера: 8 чтений + `get_merchant_context` с ограничениями данных; заглушки записи с `ChangeNotApplicable`; прогон `contract.py` | 5–7 | Самое ценное. Из них 1 день — «кампании» как одна синтетическая запись с оговоркой |
| 2 | Собственный скилл «финансы маркетплейса» (удержания, выплата, сходимость каскада) + метрики `commission`, `logistics`, `storage`, `penalties`, `payout` в `query_metrics` + термины в `metrics_intent_terms` | 3–4 | Без него агент будет рассуждать о «трафике» и «конверсии», которых нет |
| 3 | Утренний дайджест через `run_morning_digest.py` под cron: «что требует внимания: остатки, всплеск возвратов, падение выплаты» | 1–2 | Только при серверном хранении данных (раздел 4.3) |
| 4 | Тонкий сервер без состояния + пакет агрегатов из браузера + экран «что уйдёт агенту» (раздел 4.2) | 4–6 | Плюс 1–2 дня на проверку безопасности: ключ, лимиты, логи без данных |
| 5 | Интерфейс: встроить чат в наш `index.html` (без Next.js-портала из примеров) | 3–5 | Портал из `examples/*/merchant-web` тянет отдельный фронтенд на Next.js — не наш стек |
| 6 | Маркетинговый и ценовой скиллы «как есть» | 0 | Не запускать: данных о кампаниях нет, а изменения в кабинете мы всё равно не применяем. Ценовой скилл может пригодиться позже как «калькулятор цены при заданной марже после удержаний» — 2–3 дня на адаптацию `get_pricing_context` |

Итого пилот «агент читает наши цифры и отвечает на вопросы» — **12–17 дней**
по пунктам 1, 2, 4, 5. С дайджестом и серверным хранением — плюс 2–3 дня и
отдельное решение заказчика о хранении.

**Что даёт наибольший эффект первым:** пункт 1 + пункт 2 —
`performance-insights` поверх read-only бэкенда. Это единственный скилл,
который работает целиком на данных, которые у нас уже есть, ничего не
пишет и отвечает на вопрос, который финансист задаёт каждую неделю: «почему
выплата упала и какой SKU это дал». Второй по эффекту — алерты по остаткам
(`inventory-operations` в части дайджеста): остатки и себестоимость уже
грузятся в v36, дни покрытия считаются из продаж. Маркетинг — последним или
никогда: скилл ждёт кампании с бюджетом, которых в выгрузках нет.

## Приложение: что ещё стоит знать

- **Модель по умолчанию** — `claude-opus-5`, `thinking_effort="low"`
  (`config.py`, строки 18–19); извлечение памяти — `claude-haiku-4-5-20251001`.
  Бюджеты: `max_tokens=2048`, до 8 итераций инструментов за ход, таймаут 120 с.
- **Зависимости**: Python ≥ 3.11, `anthropic 0.122`, `pydantic 2.13`,
  `fastapi 0.141`, `claude-agent-sdk 0.2.139`, `mcp 1.29`. Node 22 — только
  демо-фронтенды.
- **Что проверяется кодом, а не промптом**: провенанс (изменить можно только
  карточку, которую агент прочитал в этой сессии), лимиты цен/скидок/остатков,
  одобрение человеком перед `apply_change`, SQL только `SELECT`, заблокированные
  поля `price`/`stock` в правке контента, фенсинг данных бэкенда в промпте.
  Документ `docs/safety.md` честно разделяет «enforced в коде» и «по промпту».
- **Тесты**: ~330 тестов на merchant-agent и общие пакеты; CI на Python
  3.11/3.12 с `ruff`.
- **Аутентификации в демо нет** (`docs/safety.md`); для пилота её надо
  добавлять самим.
